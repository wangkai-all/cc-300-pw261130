# 转运方案台

从零实现的仓间调拨方案比较与占用确认工具。库存以**事件流水**为唯一事实来源，方案试算不写任何库存；只有"转正式"才占用资源，"执行"才写库存流水。无第三方依赖：`node:http` + `node:sqlite` + 原生 ES module 前端。

## 运行

需要 Node.js >= 22.5（内置 `node:sqlite`）。

```bash
npm start          # http://localhost:3000，数据写入 data.sqlite
PORT=8080 DB_FILE=/tmp/demo.sqlite npm start
npm test           # 41 个用例：求解、占用、执行、HTTP、页面渲染
```

首次启动自动建表并载入本地虚构演示数据（演示日期固定为 `2026-11-16`）。页面右上角"重置演示"可恢复初始数据。

```
src/
  schema.mjs     数据库结构（事件库存、方案、占用、执行、恢复任务）
  seed.mjs       虚构演示数据：4 仓、2 SKU、7 张订单、2 条到货、1 条在途
  dates.mjs      日期工具
  inventory.mjs  事件库存推导：日终库存、可承诺量、占用累计、流水写入
  solver.mjs     纯函数求解器：最小费用流（集中）与逐单分配（分阶段）
  planning.mjs   编排：试算 / 保存 / 转正式核对 / 执行 / 撤销 / 取消 / 更正 / 延误 / 恢复
  app.mjs        HTTP API + 静态资源
public/          无构建步骤的单页前端（index.html / app.js / style.css）
test/            node --test 用例
```

## 数据模型要点

- **库存全部由 `stock_events` 推导**：`opening / receipt / receipt_correction / ship / transfer_in / transfer_out / adjust`。不存在"库存表"，因此不会出现页面数字和流水对不上。
- **可承诺量** = 当日日终预测库存 − 安全库存 − 截至当日仍未执行的正式占用（累计口径：今天被占的货，明天不会再出现）。日终预测包含已确认的到货计划，但不把未到达的在途当库存。
- **试算纯只读**：`previewPlan` 只查询，不写 `plans / reservations / stock_events`；因此可以任意比较 A/B 口径。
- **占用槽位**分三类，转正式时逐类核对：
  - `stock`：调出仓 × SKU × 发运日（本地出库同理）；
  - `lane`：线路 × 发运日的运力；
  - `demand`：对订单的承诺，防止一张订单被两个正式方案重复承诺。
- **依据指纹** `facts_hash`：库存流水 + 到货计划 + 原始订单量 + 线路 + 参数；**故意不含**其他方案的占用。于是"别人先占了货"→ 超占冲突（`OVERCOMMIT`），"到货被更正 / 订单被取消"→ 依据过期（`PLAN_STALE`），两者不会混为一谈。
- **乐观并发**：`plans.row_version`；确认时可带 `expectedRowVersion`。
- **执行与撤销**：执行写库存流水并按数量核销占用；撤销只释放剩余量（可只撤一部分），已执行部分不回滚，撤销后的余量仍可继续执行。订单取消把未执行占用置为 `lapsed` 并生成恢复任务；到货更正不静默改方案，而是标记受影响正式方案并生成复核任务。

## 两种求解口径

| 口径 | 做法 | 结果特征 |
| --- | --- | --- |
| 集中 `central` | 所有订单 × 各仓每日可承诺量 × 线路运力放进同一张最小费用流网络；缺货建模为"每件缺货成本"的兜底边 | 总成本（运费 + 操作费 + 逾期罚金 + 缺货成本）最小；稀缺库存流向最能避免缺货的订单 |
| 分阶段 `phased` | 按到期日逐单分配，每张单只挑自己单价最低的来源，先到先得 | 单看某张单/某条线路更便宜，但可能把调出仓自己的订单挤成缺货 |

演示数据刻意做成**局部便宜害了别处**：

- 集中：总成本 ¥1591，缺货 45 件（缺货成本 ¥605），运费 ¥502。武汉 SO-2601 拿满 90 件本地库存。
- 分阶段：总成本 ¥1944，缺货同为 45 件，但缺口转移到缺货成本 40 元/件的 SO-2601（缺 10 件）和广州 SO-2605（缺 25 件），缺货成本涨到 ¥1145；运费反而更低（¥315）。
- 试算页会把逐单差异和原因讲清楚：谁被挤掉、被谁以"更便宜"为由先用掉、运费省了多少、缺货多付了多少。

## 演示故事线

1. **概览**：看四仓库存、可承诺量、被占用量、事件流；可取消订单、更正到货、登记到货/延误。
2. **试算比较**：同一范围同时跑集中与分阶段，比较总成本、缺货、逾期、逐单影响，然后分别"保存为草稿"。
3. **方案与占用**：林薇先转正式；赵启明的草稿再转正式会返回 `OVERCOMMIT` 并列出每个冲突槽位（谁占了多少、上限多少）。刷新草稿后按剩余资源重算，再转正式即可。
4. **执行与回放**：对分配行做部分执行 → 撤销剩余；或整行执行到方案自动完成。每条分配都保存来源（本地/调拨/缺货）、到达日、成本分解和未满足原因。
5. **事实变化**：取消订单会释放占用并生成恢复任务；更正到货会把相关正式方案标记为依据已变；在途延误重算逾期罚金并生成恢复任务；恢复任务可一键生成恢复草稿方案。
6. **回放**：事件流按时间倒序展示谁在何时占用了什么、执行了多少、方案何时被拒绝或撤销。

## API 摘要

```
GET  /api/bootstrap                     首屏数据
GET  /api/inventory?wh=&sku=            库存 / 到货 / 在途 / 占用
GET  /api/availability?wh=&sku=         每日可承诺量曲线
POST /api/plans/preview                 同时试算两种口径（不落库）
POST /api/plans                         保存草稿
POST /api/plans/:id/commit              转正式（核对依据 + 占用；可带 rowVersion）
POST /api/plans/:id/refresh             刷新草稿
POST /api/plans/:id/revoke              撤销正式方案
POST /api/allocations/:id/execute       执行（qty 可选，支持部分执行）
POST /api/allocations/:id/return        撤销剩余（qty 可选）
POST /api/orders/:id/cancel             取消订单
POST /api/receipts/:id/correct|arrive   到货更正 / 到货登记
POST /api/transfers/:id/delay|arrive    在途延误 / 到达
GET  /api/recovery                      恢复任务
POST /api/recovery/:id/plan|dismiss     生成恢复方案 / 关闭任务
POST /api/demo/reset                    重置演示数据
```

错误统一为 `{ error, code, detail }`：`PLAN_STALE`(409)、`OVERCOMMIT`(409)、`STALE_PLAN`(409)、`BAD_QTY`(422)、`EMPTY_SCOPE`(422) 等。

## 已知边界

- 固定运费（每条线路每批一次）是阶梯成本，最小费用流里按变动成本寻优、出结果后按实际批次计入总成本；真实上线应改为混合整数模型。
- 求解范围默认 21 天、全仓全 SKU；演示数据规模下为毫秒级，未做大规模性能优化。
- 单进程 SQLite + 事务 + `row_version` 足以演示并发占用；生产环境需换成真正的多实例数据库与分布式锁。
